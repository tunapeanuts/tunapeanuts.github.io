Parquetはなぜ圧縮効率がよいのか？

Parquetの圧縮を理解する上で重要なのが符号化（Encoding）と圧縮（Compression）は別の処理であるということ．単純にファイル全体を圧縮するのではなく，列ごとの値の性質を利用して符号化を行い，その結果をさらに圧縮する．

列指向で同じ性質の値をまとめることで，繰り返しや分布の偏り，小さな差分といった規則性を利用しやすくなる．まずは符号化から見ていく．

Dictionary Encoding（辞書符号化）

頻繁に登場する値を辞書に登録し，値そのものではなく整数IDを保存する方式である．

例えば42バイトのEthereumアドレス文字列が100万件存在し，異なるアドレスが256種類しかないとする．IDは8ビット（1バイト）で表現できる．

異なる値の種類数をCardinality（カーディナリティ）と呼ぶ．基本的にCardinalityが低いほど辞書符号化との相性がよい．辞書が大きくなりすぎる場合，書き込み実装によってはPLAINに切り替わる．

データCardinality相性
成功・失敗非常に低い非常によい
国名・プロトコル名低いよい
ユーザアドレスデータによるデータによる
トランザクションハッシュ非常に高い悪い

Run-Length EncodingとBit Packing

Run-Length Encoding（RLE）

同じ値が連続して登場する場合に，値と連続回数を保存する．連長圧縮とも呼ばれる．

例えばブロック番号順に並んだトランザクションでは，同じブロック番号が連続して登場する．逆に 0, 1, 0, 1, 0, 1 のようなデータではRLEの効果は小さい．

Bit Packing（ビットパッキング）

値を表現するために必要な最小限のビット数で保存する方式である．0〜3の整数なら32ビットではなく2ビットで表現できる．

RLEとBit Packingの併用

ParquetではRLE / Bit-Packing Hybridが採用されている．同じ値が連続する部分はRLEで，それ以外はBit Packingで表現する．辞書符号化されたIDや定義・繰り返しレベルなどの保存にも使われる．

Delta Encoding（差分符号化）

値そのものではなく，直前の値との差分を保存する方式である．

最初の値に差分を順番に足していけば元の値を復元できる．

xn = x0 + ∑i=1n Δi

DELTA_BINARY_PACKED

Parquetではブロック内の最小差分を求め，各差分からそれを引いた値をミニブロック単位でBit Packingする．

データ相性
タイムスタンプ・ブロック番号よい
連番IDよい
整数のセンサ値値の変動による
ランダム整数・ハッシュ値悪い

値自体が大きくても，隣り合う値の差が小さい，あるいは差分のばらつきが小さければ効率よく保存できる．

その他の符号化アルゴリズム

Delta Byte Array

前の文字列と共通する接頭辞（Prefix）を利用する．辞書符号化では値全体の一致を利用するが，こちらは部分一致も利用できる．

Delta Length Byte Array

可変長のバイト列の長さと本体を分離し，長さをDelta Encodingで符号化する．

Byte Stream Split

固定長データをバイトの位置ごとに並べ替える方式である．似た値の浮動小数点数では特定の位置のバイトが似ることがある．

Byte Stream Split自体ではデータ量が減らない．後段の圧縮が効きやすいように並べ替えているということ．

符号化方式の比較

アルゴリズム利用する特徴
Dictionary同じ値の再登場
RLE同じ値の連続
Bit Packing値の取り得る範囲が狭い
Delta差分のばらつきが小さい
Delta Byte Array共通接頭辞
Delta Length Byte Array長さの規則性
Byte Stream Split同じ位置のバイトの類似性
PLAIN特殊な符号化を行わない

Compression Codecの基礎

ここまではデータの構造を利用した符号化の話である．ここからは符号化後のバイト列を圧縮するアルゴリズムを見ていく．まずLZ77とエントロピー符号化を理解しておくとよい．

LZ77

LZ77（Lempel–Ziv 1977）は過去に登場したバイト列を参照することで繰り返しを削減するアルゴリズムである．

Literal（そのまま保存する値），Offset（過去の参照位置），Length（コピーする長さ）などを用いる．Dictionary Encodingが列の値の一致を利用するのに対し，LZ77は任意のバイト列の一致を利用する．

Huffman Coding（ハフマン符号化）

頻繁に登場する記号には短い符号を，あまり登場しない記号には長い符号を割り当てる．出現頻度の小さいノードから順に結合して木を構成する．

4種類の記号を固定長で表現すると1記号当たり2ビット必要となる．上記の場合の平均符号長は以下の通り．

0.7 × 1 + 0.15 × 2 + 0.15 × 3 = 1.45 bit

符号表などのオーバーヘッドを無視すると，100記号を200ビットから145ビットに削減できる．

シャノンエントロピー

情報源の不確実性はシャノンエントロピーによって表される．

H(X) = −∑i pi log2 pi

上記の確率分布では H(X) ≈ 1.319 bitとなる．独立に記号を生成する情報源の可逆符号化における平均符号長の理論的な下限である．規則性や偏りが存在するほど圧縮の余地が生まれる．

圧縮アルゴリズムごとの特徴

Snappy

Googleが開発したLZ77系の圧縮アルゴリズムである．圧縮率よりも圧縮・展開速度を重視している．ハフマン符号化などの追加のエントロピー符号化を行わず，比較的単純なバイト指向の形式で保存する．PyArrowのParquet書き込みではデフォルトのコーデックとして利用されている．

LZ4

LZ4もLZ77系のアルゴリズムであり，Literal，Offset，Match Lengthなどを単純な形式で保存する．特に高速な展開処理を重視している．Parquetでは従来のLZ4コーデックは非推奨であり，LZ4_RAWが推奨されている．

GZIP

GZIPは内部でDEFLATEを使用する．DEFLATEはLZ77とハフマン符号化を組み合わせたアルゴリズムであり，繰り返しと出現頻度の偏りの両方を利用する．SnappyやLZ4より高い圧縮率が得られることが多いが，圧縮処理のCPU負荷も大きくなりやすい．

Zstandard（ZSTD）

Facebook（現Meta）が開発したアルゴリズムであり，高い圧縮率と高速な処理の両立を目指している．圧縮レベルに応じて速度と圧縮率のバランスを変更できる．

特徴的なのがFSE（Finite State Entropy）である．ANS（Asymmetric Numeral Systems）に基づき，状態遷移とビットの入出力によって記号列全体を効率よく符号化する．ハフマン符号化では個々の記号の符号長が整数ビットになるが，FSEでは平均符号長を情報理論上の限界に近づけやすい．ZSTDでは圧縮レベルを上げても展開速度への影響は比較的小さい傾向にある．

Brotli

Googleが開発した高圧縮率のアルゴリズムである．LZ77，ハフマン符号化，コンテキストモデリング，静的辞書などを利用する．テキストとの相性がよくWebページの圧縮にも利用されている．高い圧縮レベルでは圧縮時間が長くなることがある．

圧縮アルゴリズムの比較

アルゴリズム圧縮速度展開速度圧縮率
LZ4非常に速い非常に速い低〜中
Snappy非常に速い非常に速い低〜中
ZSTD速い〜遅い速い中〜高
GZIP比較的遅い中程度中〜高
Brotli中〜非常に遅い中程度〜速い高い場合がある

実際にParquetで使い分ける

データの種類と符号化

カラム特徴符号化の候補

timestamp差分の規則性Delta（整数表現）
from_addressアドレスの再登場Dictionary
to_address特定のアドレスへの集中Dictionary

これらは候補であり，ライブラリが自動的に最適な方式を選択するとは限らない．実際のデータとライブラリの対応状況を確認する必要がある．

圧縮方式の指定

Pandasでは保存時に圧縮方式を指定できる．

df.to_parquet("data.parquet", compression="snappy")
df.to_parquet("data.parquet", compression="zstd")

PyArrowを直接利用すると，圧縮レベルなども細かく指定できる．

import pyarrow as pa
import pyarrow.parquet as pq

table = pa.Table.from_pandas(df)

pq.write_table(
    table,
    "data.parquet",
    compression="zstd",
    compression_level=3,
    use_dictionary=True
)

使用されている符号化・圧縮方式の確認

import pyarrow.parquet as pq

pf = pq.ParquetFile("data.parquet")
rg = pf.metadata.row_group(0)

for i in range(rg.num_columns):
    col = rg.column(i)
    print("Column:", col.path_in_schema)
    print("Compression:", col.compression)
    print("Encodings:", col.encodings)
    print("Uncompressed:", col.total_uncompressed_size)
    print("Compressed:", col.total_compressed_size)
    print()

例えば次のような出力が得られる（数値は説明用）．

Column: protocol
Compression: ZSTD
Encodings: ('PLAIN', 'RLE', 'RLE_DICTIONARY')
Uncompressed: 1200000
Compressed: 85000

total_uncompressed_size は符号化後のParquetページの非圧縮サイズに基づく値であり，元のDataFrameのメモリ使用量ではない．また，EncodingsはColumn Chunkで使用された方式の一覧であって，全値が同じ方式で符号化されたことを意味しない．

自分のデータでベンチマークを行う

圧縮率はデータによって異なるため，同一のデータでファイルサイズ，書き込み時間，読み込み時間を測るのがよい．

import os
import time
import pyarrow as pa
import pyarrow.parquet as pq

table = pa.Table.from_pandas(df)
codecs = ["none", "snappy", "lz4", "gzip", "zstd", "brotli"]

for codec in codecs:
    path = f"benchmark_{codec}.parquet"
    start = time.perf_counter()
    pq.write_table(table, path, compression=codec)
    write_time = time.perf_counter() - start

    start = time.perf_counter()
    pq.read_table(path)
    read_time = time.perf_counter() - start
    size = os.path.getsize(path) / 1024**2

    print(f"{codec:8} size={size:.2f} MiB "
          f"write={write_time:.3f}s read={read_time:.3f}s")

実験の際はコーデックの対応状況，圧縮レベル，Row Groupサイズ，OSのファイルキャッシュ等に注意する．複数回測定してばらつきも確認するとよい．

どのアルゴリズムを選択するか？

コーデック選択する場面
Snappy頻繁な読み書き・互換性を重視
LZ4特に展開速度を重視
ZSTD大規模データの保存と繰り返し分析
GZIP広い互換性を重視
Brotli圧縮時間よりサイズを重視

大量の履歴データをSSDに保存し，何度も分析する場合は，まずZSTDの圧縮レベル3を試すとよいと思う．ただし最終的には実際のデータで比較するのが確実である．

まとめ

Parquetの圧縮効率が高い理由は単に高性能な圧縮コーデックを使用しているからではない．列指向のデータ配置，データの性質に応じた符号化，汎用的な圧縮アルゴリズムという3つが組み合わさっているのである．
