BigQueryなどで大量のデータを扱っていると，列指向という言葉を見かけることがある．一方MySQLやPostgreSQLのような一般的なデータベースは，行指向であることが多い．そもそも何が違うのか，それぞれどういう場合に使えばよいのかを整理する．

そもそも行指向・列指向とは？

行指向（Row-oriented）と列指向（Column-oriented）の違いはテーブルのデータを内部でどのように配置して保存するかという部分にある．例えば，以下のようなユーザのデータを管理するとする．

ID名前年齢所持金
1Alice201000
2Bob252000
3Carol303000

SQLを通して見るとどちらも同じテーブルである．しかし，内部でのデータの並び方が異なる．

行指向では1レコード分のデータが近くに保存され，列指向では同じ属性のデータが近くに保存される．この違いによって得意な処理が変わってくる．

行指向データベース

行指向では，例えばAliceのID，名前，年齢，所持金がまとめて保存されている．そのため，あるユーザの情報をまとめて取得したい場合に都合がよい．

SELECT *\nFROM users\nWHERE id = 1;

また，新しいユーザを登録したり，特定のユーザの情報を更新したりする場合も，レコード単位で操作できる行指向と相性がよい．

UPDATE users\nSET balance = 1500\nWHERE id = 1;

ECサイトの注文管理，銀行口座の残高管理，SNSのユーザ管理などが代表的なユースケースである．MySQL（InnoDB），PostgreSQL，SQLiteなどは基本的に行指向のストレージを利用する．

列指向データベース

一方で，ユーザ全体の平均年齢を計算する場合はどうだろうか．

SELECT AVG(age)\nFROM users;

この処理には年齢の情報しか必要ない．ID，名前，所持金を取得する必要はないということ．

列指向であれば必要な列だけを読み込めるため，大量のレコードを対象とする集計や統計分析に向いている．BigQuery，ClickHouse，Amazon Redshift，DuckDBなどが代表例である．

ただし，列指向はデータを追加できないというわけではない．大量のデータをまとめて追加する処理や追記型のデータとはむしろ相性がよい．一般に苦手なのは既存のレコードに対する頻繁な細かな更新である．

読み込み量と圧縮効率の違い

読み込み量の違い

例えば1億行，20列のテーブルがあり，1セルが8バイトであると仮定する．このうち1列だけを利用して集計するとする．

この単純な例では列指向の読み込み量は行指向の20分の1になる．数件程度のデータであれば差は小さいが，数億件，数十億件のデータになると無視できない．

圧縮効率の違い

列指向では同じ型や似た値のデータが連続して保存されるため，圧縮もしやすい．例えば国名の列を辞書符号化すると，以下のようになる．

もちろん行指向でも圧縮は可能であるが，列単位でデータの特性に合わせた圧縮方式を選べるという点は列指向の利点である．

OLTP（Online Transaction Processing）

日常的に発生する個々のデータの登録，取得，更新などを扱う処理である．例えば，ユーザの注文を登録したり，口座残高を変更したりする処理が該当する．

OLAP（Online Analytical Processing）

蓄積された大量のデータに対して，集計や統計分析などを行う処理である．例えば，1年間の売上を商品カテゴリごとに集計する処理が該当する．

ただし，検索だから行指向というわけではない．少数のレコードから多数の列を取得する検索であれば行指向，大量のレコードから一部の列を検索・集計するのであれば列指向が向いていることが多い．OLTP・OLAPは処理の分類であり，行指向・列指向は保存方式の分類なので，厳密には別の概念である．

実際のシステムでの使い分け

実際のサービスでは行指向と列指向のどちらか一方を選ぶというよりも両方を組み合わせることがある．例えば，Webサービスで発生したデータはPostgreSQLに保存し，分析に必要なデータをBigQueryへ転送するという構成である．

このようにサービスを運営するためのDBと，サービスから得られたデータを分析するためのDBを分離することで，それぞれの処理に適した保存構造を利用できる．

ブロックチェーンデータ分析の場合

Ethereumのトランザクションデータを扱う場合も同様である．例えば特定のTx Hashに対応するトランザクションの情報を取得したい場合と，数億件のトランザクションのガス代を分析したい場合では求められる処理が異なる．

研究で利用しているBigQueryやParquetも，列指向という考え方に基づいている．ただし，BigQueryは分析基盤であり，Parquetは列指向のファイルフォーマットである．Parquet自体がデータベースというわけではない．

例えば，Ethereumのトランザクションデータを保存したテーブルから，送信元アドレスとタイムスタンプだけを取得したいとする．

SELECT from_address, block_timestamp\nFROM transactions;

列指向であれば，分析に必要な列だけを読み込むことができる．BigQueryのオンデマンド課金では処理するデータ量を抑えることにもつながる．また，取得したデータをParquet形式で保存しておけば，対応する分析エンジンから必要な列だけを読み込むこともできる．

まとめ

かなりざっくり言えば，以下のような理解でよいと思う．

行指向：特定の対象について多くの情報を取得・更新したい場合．

列指向：多くの対象について特定の情報を取得・分析したい場合．

ある人のデータを検索して取得したり，個々のデータを頻繁に更新したりするユースケースが多いのであれば行指向が向いている．一方で，ある列のデータを頻繁に分析したり，大量のデータをまとめて取得して分析したりするような既存データの個別更新が少ないユースケースであれば列指向が向いている．ただし，全列を一括取得するだけで必ず列指向が有利になるわけではない．

結局，DBの保存方式を考える際には，どのくらいの行に対してどのくらいの列を利用するのか，どの程度更新するのかというアクセスパターンを見ることが重要なのだと思う．
