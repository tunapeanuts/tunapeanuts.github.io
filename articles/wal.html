データベースの内部構造を調べていると，WAL（Write-Ahead Logging）という用語が登場する．なぜデータベースは実際のデータとは別にログを管理する必要があるのか，障害復旧と書き込み性能という観点から整理する．

そもそもWALとは？

WALとは，変更済みのデータを永続ストレージに書き込む前に対応する変更内容をログとして永続化する仕組みである．Write-Ahead Loggingという名前の通り，実際のデータの書き込みよりも先にログを書き込む．

例えば，Aliceの銀行口座の残高を1000円から2000円に変更するとする．

UPDATE accounts
SET balance = 2000
WHERE name = 'Alice';

わざわざ二段階の書き込みを行う理由は主に障害からの復旧と書き込みの効率化である．

なぜWALが必要なのか？

例えば，AliceからBobへ500円を送金する処理を考える．

ユーザ送金前送金後
Alice1000円500円
Bob1000円1500円
合計2000円2000円

この処理には2つのデータ更新が必要になる．もしAliceの残高を減らした直後にサーバがクラッシュしたらどうなるだろうか．

このような問題を防ぐため，DBではWALとトランザクション管理を組み合わせている．ACID特性のAtomicity（原子性）やDurability（永続性）に関係する仕組みである．WALだけでACIDのすべてが実現されるわけではない．

WALによる障害復旧の仕組み

先ほどの送金処理の変更内容をWALに記録しておく．

BEGIN Transaction 001

Alice: 1000 → 500
Bob:   1000 → 1500

COMMIT Transaction 001

実際にはDB固有のバイナリ形式で記録されるが，概念的にはこのようなイメージである．

復旧処理には主にREDOとUNDOという考え方が存在する．

処理意味
REDOログを基に変更を再適用する．
UNDO未完了の変更を取り消す．

コミット済みの変更が反映されていなければ，必要に応じてREDOを行う．未コミットの変更は取り消したり，無効なデータとして扱ったりする．具体的な方式はDBによって異なる．例えばPostgreSQLでは，WALによるREDOとMVCCによる可視性管理を組み合わせている．

WALはなぜ書き込みを高速化できるのか？

ログとデータの両方を書き込むため，一見するとWALを利用した方が遅くなるように思える．しかし，コミット時に必要な書き込みを逐次書き込み（Sequential Write）に集約できるという利点がある．

一般にランダム書き込みよりも逐次書き込みの方が効率がよい．さらに通常の永続性設定では，コミットに必要なWALが永続化されていれば，データページの書き込みが完了する前に処理の成功を返せる．

データページへの書き込みは後からまとめて行えるため，同じページへの複数の更新を一度の書き込みにまとめることもできる．ランダム書き込み自体がなくなるわけではないが，コミットのたびに待つ必要がなくなるということ．

また，複数のトランザクションのWAL永続化をまとめて行うGroup Commitという最適化も存在する．

Checkpointとは？

WALに変更内容を追加し続けると，ログファイルが際限なく大きくなってしまう．障害が発生するたびに最初からすべてのログを読み直すのも非効率である．そこで利用されるのがCheckpoint（チェックポイント）である．

Checkpointでは，復旧の基準となる位置を記録し，必要なデータページを永続ストレージに反映する．

Checkpointによって復旧などに不要になった古いWALを削除・再利用できるようになる．ただし，レプリケーションやバックアップなどのために古いWALを保持する場合もある．

WALとデータファイルの全体像

重要なのはメモリ上の変更順序ではなく，対応するWALが永続化される前に変更済みのデータページを永続化しないという順序である．

WALを利用するデータベースと用途

WALやそれに相当する仕組みは多くのDBで採用されている．

データベースログの名称
PostgreSQLWAL
MySQL（InnoDB）Redo Log
SQLiteWAL（WALモード）
RocksDBWAL
LevelDBWrite-Ahead Log

また，WALは障害復旧だけでなく，DBによっては次のような用途にも利用される．

用途内容
Crash Recoveryクラッシュからの復旧
Replication他のDBへの変更内容の伝達
Point-in-Time Recovery特定時点の状態への復元
CDCデータの変更内容の外部配信

ParquetにはWALが存在するのか？

Parquetと比較すると，WALの役割がより分かりやすい．

比較項目PostgreSQLParquet
分類データベースファイル形式
頻繁な個別更新想定している基本的に想定していない
トランザクション管理ありなし
WALありなし
障害復旧機構DBが管理外部システムに依存

Parquet自体はデータの保存形式なので，WALを持たない．一方DuckDBのように列指向のDBであっても，WALは存在する．つまり，行指向・列指向というデータの配置方法と，WALという障害復旧・永続化の仕組みは別の概念である．

まとめ

用語役割
WAL変更内容を先に記録する．
Buffer Poolメモリ上でデータを管理する．
REDO変更内容を再適用する．
UNDO未完了の変更を取り消す．
Checkpoint復旧の基準となる位置を管理する．
Data File実際のデータを永続的に保存する．

端的に言えばWALとは，変更済みのデータを永続化する前に対応する変更の記録を永続化しておく仕組みである．これによって安全性と書き込み性能を両立できる．
